# Wave 2 S0 Audit A1 - Journal Contract Extension

Verdict: **MAJOR REVISION REQUIRED**

S0 is tightly scoped and most of the surface is correct: `TxObservationSource.P2p` is present, no main-slice implementation files landed, the existing `AppendAsync(TxMessage, CancellationToken)` path is untouched, and the projection test uses the W1 Raven-gated `[SkippableFact]` convention. One contract mismatch blocks opening S1-S8: the new source-neutral overload does not honor the documented duplicate-return semantics.

## Findings

### H1 - Source-neutral `AppendAsync` returns `true` for duplicate journal writes

Where:
- `docs/stream-tasks/bsv-mempool-observer-wave/slices.md:60-63`
- `src/Dxs.Consigliere/BackgroundTasks/TxObservationJournalWriter.cs:73-80`
- `src/Dxs.Common/Journal/ObservationJournalAppendResult.cs:14-16`
- `tests/Dxs.Consigliere.Tests/BackgroundTasks/TxObservationJournalWriterSourceNeutralTests.cs:22-32`

Evidence:
- S0.2 requires the new overload to return `true` on append and `false` on duplicate or invalid input.
- The implementation builds the request and awaits `observationJournal.AppendAsync(...)`, but discards `ObservationJournalAppendResult` and unconditionally returns `true`.
- `ObservationJournalAppendResult` exposes `IsDuplicate`, so the overload has the information needed to implement the contract.
- The source-neutral tests only use an appender that always returns `IsDuplicate = false`; there is no duplicate-result test.

Why it matters:
- The bool return is part of the frozen S0 contract that S4/S5 will consume. Returning `true` for duplicates makes callers believe a new observation was appended when the journal actually deduped it.

Recommendation:
- In the new source-neutral overload only, capture the append result and return `!result.IsDuplicate`.
- Add a source-neutral unit test with an appender returning `new ObservationJournalAppendResult(existingSequence, true)` and assert the overload returns `false`.

### M1 - Payload parameter is not annotated nullable in the implementation signature

Where:
- `docs/stream-tasks/bsv-mempool-observer-wave/slices.md:40-44`
- `src/Dxs.Consigliere/BackgroundTasks/TxObservationJournalWriter.cs:56-60`
- `tests/Dxs.Consigliere.Tests/BackgroundTasks/TxObservationJournalWriterSourceNeutralTests.cs:69`
- `tests/Dxs.Consigliere.Tests/BackgroundTasks/TxObservationJournalWriterSourceNeutralTests.cs:94`
- `tests/Dxs.Consigliere.Tests/BackgroundTasks/TxObservationJournalWriterSourceNeutralTests.cs:106`

Evidence:
- S0.2 specifies `RawTransactionPayloadReference? payload`.
- The implementation signature is `RawTransactionPayloadReference payload`.
- Tests call the overload with `payload: null`, and the method behavior supports null, but the public source signature does not document that contract.

Why it matters:
- The overload is a contract-freeze surface. Downstream callers should see the optional payload contract directly in the signature, not infer it from tests or XML comments.

Recommendation:
- Annotate the new overload payload parameter as nullable. If enabling nullable annotations in the file creates follow-on warnings, annotate the related private payload helper return type consistently.
